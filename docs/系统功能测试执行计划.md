## 1 计划概述

### 1.1 编制依据与目标

本计划将《考试宝系统功能测试方案》中设计的 **610 条测试用例** 转化为可执行、可追踪、可自动化的测试任务，目标：

| 目标 | 度量 |
|------|------|
| 全覆盖 | 610 条用例 100% 映射到阶段与责任人，零遗漏 |
| 可执行 | 每条用例有明确执行命令/步骤与判定方法 |
| 可自动化 | ≥85% 用例由 AI 智能体自动执行，人工仅承担抽检与验收 |
| 可门禁 | 4 个阶段门禁（G0–G4），未达标不得进入下一阶段 |
| 可追溯 | 用例 ↔ 阶段 ↔ 任务 ↔ 智能体 ↔ 缺陷 ↔ 报告 全链路可追溯 |

### 1.2 覆盖度对应总表（测试方案 → 执行计划）

| 门禁 | 位置 | 通过条件（全部满足） | 未通过处理 |

| **G3** | S3 结束 | ① BB 通过率 ≥97% ② 边界异常通过率 ≥95% ③ P0=0、P1≤2(有缓解) ④ 安全用例 100% ⑤ 并发用例 100% | 阻断，缺陷修复+定向回归 |

#### 4.1.1 测试目标
确认三端环境可正常启动、依赖完整、测试数据可用，主链路（登录→答题→交卷）可端到端跑通。

#### 4.1.2 任务要点
1. 后端：受管 venv 依赖安装、Django 迁移、`init_admin` + 全套 seed 命令执行
2. 前端：`npm install` + `npm run dev` 启动，`/api` 代理连通
3. 小程序：微信开发者工具打开，`urlCheck=false`，后端地址指向 `127.0.0.1:8000`

## 5 AI 智能体自动化执行方案

### 5.1 设计原则

| 原则 | 说明 |
|------|------|
| **分层自治** | 每阶段由专职智能体负责，互不越界，通过 ORCH 协调 |
| **契约驱动** | 每个智能体有明确的输入/输出 JSON 契约，便于编排与重试 |
| **门禁阻断** | 未通过门禁不得进入下一阶段，防止缺陷向后传播 |
| **幂等可重放** | 每个任务可重放，测试数据隔离，避免副作用累积 |
| **人在回路** | 关键决策（P0 缺陷、发布）必须人工确认，AI 不越权 |
| **全链可溯** | 用例→任务→智能体→结果→缺陷→报告 全程留痕 |

### 5.6 结果验证机制（四层）

| 层级 | 名称 | 方法 | 作用 |
|------|------|------|------|
| **L1 断言级** | 框架断言 | TestCase/assert 直接判定 | 单条用例正确性 |
| **L2 交叉验证** | 二次执行 | 失败用例重跑、关键用例三次取多数 | 消除偶发/flaky |
| **L3 门禁级** | 阈值校验 | 通过率/覆盖率对照门禁 | 阶段质量把关 |
| **L4 人工级** | 抽检复核 | ≥5% 用例人工复核 + 缺陷复核 | 防 AI 误判 |

### 5.7 异常处理机制

| 异常类型 | 检测方式 | 处理策略 | 升级条件 |
|----------|----------|----------|----------|
| 环境不可用 | 健康检查失败 | ENV 重试3次 → 告警 ORCH | 3次失败 → 暂停并通知人工 |
| 真缺陷（断言失败） | 断言+traceback | DEF 登记 → 按级别分派修复 → 回归 | P0 → 立即阻断 |
| 环境问题 | 连接/依赖错误 | ENV 修复 → 重跑 | 连续2次 → 人工介入 |
| 用例缺陷 | 系统正确但断言语义不符 | DEF 修正用例 → 复跑 | 批量 → 用例评审 |
| 执行超时 | 超阈值 | 快照 → 中断 → 降级跳过并记录 | 核心用例 → 人工 |
| 数据污染 | 用例间相互影响 | 隔离 → 重建测试库 → 重跑 | 频繁 → 重构用例 |
| flaky（结果不稳） | 多次结果不一致 | 标记 flaky → 隔离 → 人工分析 | 影响门禁 → 人工 |
| AI 任务卡死 | 心跳超时 | 终止 → 重启 → 从检查点续跑 | 2次 → 人工 |

### 8.2 质量评分模型

```
质量得分 = 0.30×用例通过率 + 0.20×覆盖率得分 + 0.20×(1-缺陷密度归一)
         + 0.15×缺陷修复率 + 0.15×自动化率

评级：
  ≥ 90  → 优（可直接发布）
  80–89 → 良（修复P1后发布）
  70–79 → 中（修复P0+P1后评审发布）
  < 70  → 差（不予发布）
```
